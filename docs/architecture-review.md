# Architecture review — deepening candidates

A deep-modules review (small interface, large hidden implementation, tested through that interface) of the AI/prompt layer, the analysis pipeline, and the two chat surfaces surfaced seven candidates where shallow or duplicated code could be collapsed into a deeper module. Ranked by the deletion test (would inlining the module concentrate real complexity, or just move a pass-through). **#3 has been actioned** — see [ADR-0001](adr/0001-chat-transport-as-async-generator.md) and `src/components/chat-widget.tsx`. The rest are an open backlog, not commitments.

| # | Candidate | Strength | Files |
|---|---|---|---|
| 1 | **One error-taxonomy seam, not three.** `classify-error.ts` is used two ways and reimplemented inline a third time in the chat route, which invented a 4th code (`upstream_failed`) the shared classifier can't produce — the taxonomy has already forked, visible in the message-key sets. Reshape to a single-error `classifyAiError`, used by all three call sites. | Strong | `src/lib/ai/classify-error.ts`, `src/app/api/chat/route.ts`, `src/app/(app)/help/actions.ts`, `src/app/(app)/contracts/[id]/analyze-actions.ts` |
| 2 | **Collapse device-trust wiring into `device.ts`.** The secret-fetch → header-read → `trust_device` RPC sequence is copy-pasted verbatim in two auth actions, untested at either call site; `resendCode`/`resendChallenge` are identical bodies. Grow a `trustCurrentDevice(days?)` and one `resendVerificationCode(purpose)`. | Strong | `src/app/(auth)/verify/actions.ts`, `src/app/(auth)/challenge/actions.ts`, `src/lib/auth/device.ts` |
| 3 | **One chat shell behind two chat adapters.** ✅ Done. ~150 lines of duplicated chat chrome collapsed into `ChatWidget`; contract chat and the product helper are now thin adapters. | Strong | `src/components/chat-widget.tsx`, `src/app/(app)/contracts/[id]/chat-panel.tsx`, `src/app/(app)/help/help-chat.tsx` |
| 4 | **One SSE frame reader, two frame formats.** The buffer/split/trailing-partial-frame algorithm is reimplemented independently server-side (`streamGeminiText`) and client-side (`chat-panel.tsx`). A shared `readSseFrames(reader)` yields raw frames; each side keeps its own line-level parsing. | Worth exploring | `src/lib/ai/router.ts`, `src/app/(app)/contracts/[id]/chat-panel.tsx` |
| 5 | **Name the repair-pipeline seam inside `extractJson`.** Four JSON-repair heuristics (fence-strip, homoglyph, stray-backslash, balanced-bracket) are threaded into nested try/catch in a specific undocumented order; a fifth requires understanding the whole call chain. Make the pipeline a first-class ordered list of named passes. Speculative until a fifth incident is on the horizon. | Worth exploring | `src/lib/ai/prompts.ts` |
| 6 | **Give `analyzeContract` an `AnalysisStore` seam.** The function talks to raw Supabase query-builder chaining inline, so its test hand-emulates PostgREST's chaining protocol (56 lines just to fake one table). Intent-level methods (`findCachedAnalysis`, `startAnalysis`, `saveResults`) would make the interface the test surface. | Worth exploring | `src/app/(app)/contracts/[id]/analyze-actions.ts`, `tests/app/analyze-partial-failure.test.ts` |
| 7 | **Fold the retryable-response check into one helper.** The same 2-line `status >= 500 ? retryable : throw` shape is retyped four times in the router. A shared `assertOk(response, label)`, each provider keeping its own inline comment. Minor. | Speculative | `src/lib/ai/router.ts` |

Not flagged despite churning: `src/lib/ingest/{parse,segment,checksum}.ts` read as genuinely deep already (substantial well-tested heuristics behind small stable interfaces, no duplication). The auth `codes`/`device`/`guards` modules are individually fine — the duplication in #2 lives in how the *action* layer calls them, not the modules themselves.
